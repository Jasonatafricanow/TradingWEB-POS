# 移动端 POS 性能提升与低配置 Android 优化报告

日期：2026-08-09

优化分支：`codex/mobile-pos-performance`

基线：`6f67f67`（只加入测量标记与基准脚本，尚未加入性能优化）

优化应用代码：`56e3aaa`；最终分支在此基础上增加 Windows 可复现构建脚本

## 结论

本轮优化已完成并通过全量自动化回归。连接设备上 20 次基线与 20 次优化版交错冷启动的合并结果为：Android 首帧 `TotalTime` 中位数由 **333 ms 降至 274.5 ms，改善 17.6%**；P95 由 **354 ms 降至 344 ms，改善 2.8%**。优化版存在一次 452 ms 离群启动，因此不能宣称尾延迟已完全解决。

启动阶段拆分使首帧更早出现，但 `app_start -> shell_mounted` 的内部就绪标记中位数由 56.11 ms 增至 71.21 ms，增加 15.10 ms。也就是说，本轮取得的是“更快显示可见界面、把非安全关键工作移到后面”的收益，而不是所有启动阶段都同步缩短。

发布侧新增单 ABI ARM64 构建。与仓库中 2026-07-19 的 96,892,307 字节 universal APK 相比，新 ARM64 APK 为 39,405,435 字节，减少 **59.3%**。其中主要收益来自不再向 ARM64 平板分发 x86、x86_64 和 armeabi-v7a 原生库；优化版与同配置 ARM64 基线 APK 相比反而增加 26,804 字节（0.07%），因此不能把 59.3% 归因于 JS 代码压缩。

当前实机是 Samsung SM-F7070、Android 13/API 33、约 8 GB 内存，并非低配置平板。因此本报告认证的是同设备相对提升、构建体积与代码级低端适配；**2 GB/3 GB Android 平板上的内存、滚动卡顿和长时间稳定性仍未认证**。

## 实测结果

| 指标 | 基线 | 优化后 | 变化 | 判定 |
|---|---:|---:|---:|---|
| Android `TotalTime` 中位数，20 次 | 333 ms | 274.5 ms | -17.6% | 改善 |
| Android `TotalTime` P95，20 次 | 354 ms | 344 ms | -2.8% | 小幅改善 |
| Android `TotalTime` 最大值 | 361 ms | 452 ms | +25.2% | 存在离群退化 |
| `app_start -> shell_mounted` 中位数 | 56.11 ms | 71.21 ms | +26.9% | 延后 15.10 ms |
| ARM64 APK | 39,378,631 B | 39,405,435 B | +0.07% | 性能标记与实现有小幅体积成本 |
| 旧 universal APK -> 新 ARM64 APK | 96,892,307 B | 39,405,435 B | -59.3% | 分发体积显著改善 |

测量采用 A-B-A-B 顺序：优化 10 次、基线 10 次、优化 10 次、基线 10 次；每组另有 2 次预热。每次先 `force-stop`，再用 `adb shell am start -W` 启动。两个 APK 均为 Release、Hermes、仅 `arm64-v8a`，并通过不同 SHA-256 确认没有误用同一产物。原始样本与哈希固化在 [A/B 汇总证据](evidence/2026-08-09-android-ab-summary.json)。

`gfxinfo` 每组最后只包含 13–33 帧，且没有自动化滚动手势，样本不足以认证卡顿率；内存也只是每组最后一次启动后的单点快照，PSS 波动方向不一致。因此本轮不对帧卡顿率或内存下降给出百分比结论。

## 已实施优化

1. **启动水合分层**：根节点只等待身份、设置、班次和语言等安全关键状态；购物车在进入业务标签页时再水合，避免所有持久化状态共同阻塞首帧。
2. **后台工作统一调度**：同步、审计上传和遥测从固定计时器及多套 `AppState` 监听合并为一个交互完成后的协调器；加入 single-flight、会话/数据源身份复核和按需触发，减少空闲轮询、并发争用与错误会话上传。
3. **缩小持久化数据**：购物车、设置、班次和审计 store 使用显式 `partialize`，只写入恢复业务所需的耐久字段，不再把 action、临时状态和上传过程状态写入 AsyncStorage。
4. **列表与渲染隔离**：商品单元格独立并 `memo`；主要 FlatList 统一限制首批渲染、批量大小和窗口；页面改用细粒度 Zustand selector 与稳定回调，减少无关状态变化造成的整页/整表重渲染。
5. **搜索限流与竞态保护**：客户搜索增加 300 ms 防抖；商品、客户查询加入 latest-request guard，旧请求不能覆盖新结果，降低快速输入时的网络、解析和渲染抖动。
6. **启动模块延迟求值**：数据源改为按需创建并缓存，Metro 开启 `inlineRequires`。生产 bundle 模块数由记录基线的 1,151 降至 1,148；bundle 字节由 3,094,118 增至 3,101,450（+0.24%），说明收益来自求值时机而非文件变小。
7. **可重复测量与发布**：新增运行时性能标记、严格失败的 Android 基准脚本、ARM64 APK/AAB 构建入口，以及针对中文长路径的 ASCII 临时 worktree 构建流程。旧 APK如果不包含当前性能标记会被基准脚本拒绝。
8. **测试稳定性**：i18n provider 暴露确定性的 ready/initialLocale 合约，消除了 ManagerPinGate Native 测试的异步语言初始化超时。历史全量 Native 基线为 8 套件中 1 个失败、约 104.7 秒；最终为 9/9 套件、24/24 测试通过，Jest 报告 19.45 秒。这个提升属于开发反馈速度，不等同于应用运行速度。

## 对低配置平板的实际价值

这批改动把性能压力从“启动时全部执行、状态变化时广泛重渲染、后台任务周期性抢占”改为“安全关键路径优先、业务路径按需、列表受控、后台工作串行”。这些优化不依赖更高 Android API 或新增大型运行时库，对 CPU 较慢、I/O 较慢和内存较小的设备尤其有利。

不过，当前不能把“低配置兼容性提升”量化为内存下降 15% 或卡顿下降某个百分比。要完成正式低端认证，需要在至少一台 2 GB/3 GB RAM、较低端 ARM64 SoC 的 Android 10–13 平板上执行：冷启动 50 次、500/2,000 商品列表滚动、连续扫码加购、离线队列积压与恢复、8 小时前台运行，并记录 Perfetto、`gfxinfo`、PSS 峰值和 OOM/ANR。

## 优化经验

- 首帧、业务可用、后台稳定是不同指标。只看 `am start -W` 会遗漏延迟水合的后续成本，只看 JS 标记又会遗漏 Android 首帧收益，必须同时保留。
- 对 Zustand/AsyncStorage 应用，先缩小订阅面和持久化面，通常比替换状态库风险更低，也更容易用现有测试证明语义不变。
- 低端设备最怕周期性小任务叠加。把多个生命周期监听、定时器和上传流程合并为 single-flight 协调器，比单纯缩短某个函数更能减少偶发卡顿。
- FlatList 参数不是越激进越好。小首批、小窗口可减轻内存和首次渲染，但需要真实低端设备滚动测试来防止白屏；因此本轮采用保守统一值，没有引入 FlashList 等新依赖。
- ABI 分发是体积优化，不应伪装成代码优化。ARM64 专用 APK显著减小下载和安装压力，但应用代码本身并未因此减少内存占用。
- Windows 下 React Native 新架构构建会同时踩到 Ninja 260 字符限制和中文路径/Hermes 临时文件问题。可复现方案是从同一提交创建真实 ASCII 短路径 worktree，而不是仅用 `subst` 路径别名。
- 未经验证的高风险开关不应进入结果。本轮没有启用 R8/资源 shrink、替换存储引擎或大规模拆分 TradingWEB adapter；这些改动需要独立的 Release 回归和收益证明。

## 剩余边界

- 尚无低配置实机，不能签署低端设备性能认证。
- 优化版一次 452 ms 启动离群值说明尾延迟仍需用 50+ 次采样和 Perfetto 定位。
- `shell_mounted` 延后约 15 ms，需要在真实登录态/有班次/大购物车数据集上验证是否值得进一步把班次恢复移出根安全门。
- R8、资源 shrink、基线 Profile 与按 ABI 的 AAB 商店交付尚未完成收益/兼容性验证。

总体判断：本轮已得到**可复现的首帧中位数提升、明显更小的 ARM64 分发包、低端友好的架构路径和完整回归保护**；但没有证据支持“整体提速 30%”或“内存需求下降 15%”的结论，低端硬件认证仍是下一道交付门槛。
