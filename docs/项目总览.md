## 一、项目目标

这是基于 TradingWEB 开发的线下移动 POS。目标不是单独维护第二套交易系统，而是形成以下职责边界：

- **TradingWEB**：订单、权威价格、支付记录、退款、库存、员工、班次、履约和审计的唯一真相源。
- **移动 POS**：门店交互、扫码、打印、钱箱、本地展示以及离线请求快照。
- **Mock 模式**：仅用于演示和离线开发，不得与真实 TradingWEB 业务状态混用。

完成标准不是“页面已经存在”，而是关键链路具备事务一致性、幂等、权限、自动化测试、真实后端验证和真机证据。

## 二、当前架构

```text
Expo Router 页面
  ├─ 收银 / 购物车 / 结账 / 订单 / 客户 / 商品
  ├─ 班次 / 报表 / 采购 / 审计 / 设置
  │
  ├─ Zustand：Auth / Cart / Shift / Pending / Audit / Settings
  ├─ PosDataSource
  │    ├─ MockDataSource
  │    └─ TradingWebDataSource → HttpClient → TradingWEB POS API
  └─ Hardware
       ├─ ScannerHub：相机 / HID / BLE 预留
       └─ PrinterManager：系统打印 / TCP / BLE / USB 预留
```

持久化使用 AsyncStorage；token 使用 Expo SecureStore。页面不应直接依赖 TradingWEB 原始响应，后端差异集中在 adapter；高风险交易编排最终必须下沉到 TradingWEB 事务服务。

## 三、不可变架构决策

### 1. ID

- 所有跨系统实体 ID 使用 UUID/string；POS 统一类型为 `EntityId = string`。
- ID 禁止使用 `Number()` 或 `parseInt()`；金额和库存数值不受此限制。
- Mock 使用稳定、带命名空间的字符串 ID。

### 2. 金额与价格

- POS 内部金额使用整数分；HTTP 金额使用明确的十进制字符串。
- TradingWEB 从数据库读取商品/变体权威价格，不能相信客户端上传单价。
- POS 预览与服务端核算不一致时阻断确认并提示刷新，不能静默覆盖。

### 3. 错误与离线

- 网络错误、5xx 才能进入自动重试范围。
- 401/403、校验错误和幂等冲突必须进入明确 blocked/人工处理状态。
- 待同步真实订单不得在迁移或清理中静默删除。

### 4. 幂等与事务

- checkout、refund、exchange、stock adjustment、purchase receive、shift close 都需要独立幂等键。
- 同一 key + 同一请求可以重放已存结果；同一 key + 不同请求必须 409。
- 退款、换货、库存和支付记录必须由 TradingWEB 在单事务内完成，不能由页面串联多个远程副作用。

### 5. 权限与操作员

- 账号登录与当班操作员是两层身份。
- PIN 只保存加盐哈希；失败次数按员工隔离。
- 高风险动作需要一次性审批令牌；没有可用 manager/admin 时必须阻断，不能自动放行。

### 6. 库存

- 目标真相源是 TradingWEB inventory 行账。
- `product_variants.stock` 只作为过渡兼容/派生汇总，关闭回退前必须完成回填和对账。

## 九、范围边界

当前计划明确不做：

- 内置第三方支付收单终端集成；当前支付是记账式。
- 在交易完整性、权限和同步可靠性完成前扩展会员、积分或复杂营销平台。
- 未经目标硬件验证就宣称 USB、BLE 专有扫码或钱箱普遍兼容。
- 用 POS 本地状态替代 TradingWEB 的订单、库存和审计真相源。
